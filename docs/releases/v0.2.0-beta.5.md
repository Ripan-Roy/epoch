# Epoch v0.2.0-beta.5

Epoch beta.5 adds a bounded migration edge for selected Redis, Apache Kafka,
and RabbitMQ clients. The new `epoch-compat` Rust process translates documented
wire operations into Epoch's existing authenticated and fenced Cache, Stream,
and Queue APIs; it does not introduce a second storage engine or broaden native
durability claims.

The release remains a private-beta evaluation build. Compatibility is an exact
allowlist backed by named released clients, not a claim of full product parity.

## Published artifacts

The verified tag workflow publishes these exact multi-platform OCI manifests
for `linux/amd64` and `linux/arm64`:

- `ghcr.io/ripan-roy/epoch-node:v0.2.0-beta.5`
- `ghcr.io/ripan-roy/epoch-control:v0.2.0-beta.5`
- `ghcr.io/ripan-roy/epoch-operator:v0.2.0-beta.5`
- `ghcr.io/ripan-roy/epoch-cli:v0.2.0-beta.5`
- `ghcr.io/ripan-roy/epoch-compat:v0.2.0-beta.5`

Each exact-tag manifest is assembled from immutable native-runner digests,
inspected as non-root, signed keylessly with Sigstore, and accompanied by
BuildKit/GitHub provenance plus separate SPDX SBOM attestations and release
assets for both platforms. The complete set contains ten platform-specific
SBOM assets. Epoch does not publish `latest`. Package-manager SDKs, raw binary
archives, OS installers, and Helm charts remain deferred.

## Highlights

- Redis clients can negotiate RESP2/RESP3 and use the documented binary-safe
  string, conditional set, multi-key, signed counter, TTL/expiry, pipeline, and
  client-setup subset against one configured Epoch Cache.
- Kafka Java producers and manual consumers can discover existing Streams,
  produce/fetch records, read earliest/latest offsets, find the compatibility
  coordinator, and commit/fetch durable checkpoints. Produce supports Kafka
  gzip, Snappy, LZ4, and Zstandard record batches.
- RabbitMQ Java clients can authenticate with AMQP 0-9-1 PLAIN, verify existing
  Queues, use the default or declared direct exchange, publish with confirms,
  consume by push or `basic.get`, apply QoS, and ack/reject/nack/requeue native
  Queue leases.
- Redis CLI 8.8.2, Apache Kafka Java client 4.3.1, and RabbitMQ Java client
  5.34.0 are asserted at runtime and execute their supported paths through the
  real listeners. Separate black-box tests prove authenticated native requests,
  resource-generation/tablet-epoch/leader-term fencing, linearizable reads,
  payload translation, and response/error mapping.
- Kafka record counts are preflighted before decoder allocation. All compression
  formats share a cumulative 4 MiB expansion bound, Zstandard windows are
  capped, and one Produce partition becomes one canonical native Stream batch
  with whole-batch visibility.
- Runtime backend and AMQP credentials are required rather than embedded.
  Configuration debug output redacts secrets, endpoint URLs cannot carry
  credentials, HTTP responses stream under a hard limit, and unsupported AMQP
  routing semantics fail closed.
- `epoch-compat scan` emits the bounded `epoch.compatibility-scan/v1` text or
  JSON report and can fail migration CI on partial, unknown, or unsupported
  declared features.
- The compatibility gateway joins the tag-only OCI supply chain as the fifth
  signed non-root component, and the exact matrix, examples, scanner, security,
  retry behavior, and non-claims are visible on GitHub Pages.

## Compatibility and migration

Compatibility targets are exact subsets. Existing Redis/Kafka/RabbitMQ data is
not imported automatically: provision the corresponding Epoch Cache, Stream,
or Queue first, scan the application's declared feature use, run representative
traffic in staging, and then change the client endpoint.

Redis database selection is limited to database 0, and multi-key writes commit
independently. Kafka topics are existing same-named Streams; manual partition
assignment is the supported consumer mode. One Produce partition must contain
1–1,000 records, fit 4 MiB after decompression, and fit the native 360 KiB
compressed proposal limit. AMQP declarations verify existing Queues and only
direct routing is implemented.

A lost connection after an uncertain native mutation is an unknown outcome.
The gateway does not retry a non-idempotent mutation under a fresh identity;
applications should supply their own stable deduplication key where retries can
cross an acknowledgement boundary.

## Install and try

Resolve and verify immutable digests before use. For a loopback evaluation from
source:

```shell
git clone https://github.com/Ripan-Roy/epoch.git
cd epoch
git checkout v0.2.0-beta.5
cargo run -p epoch-compat -- \
  --endpoints http://127.0.0.1:7601 \
  --token epoch-dev-admin-v1 \
  --redis-cache sessions \
  --redis-password local-redis-password \
  --kafka-advertised-host 127.0.0.1 \
  --amqp-username epoch \
  --amqp-password local-amqp-password
```

Provision `sessions`, `events`, and `jobs` as the matching Epoch resources
before connecting clients. Follow the public protocol-compatibility guide for
exact commands, APIs, client examples, and the migration scanner.

## Beta limitations

- Redis hashes/lists/sets/sorted sets, transactions, scripts, Pub/Sub, Streams,
  cluster mode, and modules are not exposed.
- Kafka consumer-group membership/rebalancing, idempotent and transactional
  producers, admin mutations, SASL/ACL APIs, and topic creation are not exposed.
- AMQP fanout/topic/header exchanges, server-named queues, transactions,
  mandatory returns, AMQP 1.0, and listener-side TLS are not exposed.
- The listeners must remain private or behind a TLS/authenticating ingress.
  Combined exact-client testing against a faulted real regional cluster,
  differential/fuzz evidence, MQTT, load/soak parity, and a production SLO are
  separate gates.
