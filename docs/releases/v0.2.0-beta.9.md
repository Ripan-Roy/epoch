# Epoch v0.2.0-beta.9

Epoch beta.9 turns the existing learner-first voter replacement primitive into
an automatic, policy-driven regional control loop. Operators can declare rack
separation or exclude a physical node, and Epoch chooses and executes one safe
repair at a time without rewriting customer data or consuming an extra customer
resource generation.

This remains a private-beta evaluation release. Automatic motion is serialized
per resource and requires fresh complete topology; fleet-wide transactional
reservation, split/merge, Kubernetes rack attestation, and production placement
SLOs are not claimed.

## Highlights

- Placement policy adds `minimum_racks` and `excluded_node_ids` alongside
  allowed regions, minimum zones, and required node class.
- Rust nodes report an explicit validated rack. Older or unconfigured nodes use
  the single safe compatibility domain `unassigned`; Epoch does not infer racks
  from zone names.
- New three- and five-voter tablets use exact bounded domain-completion
  look-ahead, including correlated zone/rack layouts, across 3–1,024 physical
  nodes. An impossible joint layout returns
  `incompatible_failure_domains` before Catalog mutation.
- Go evaluates legal one-voter targets deterministically. It prioritizes
  excluded/missing/wrong-policy voters, then zone/rack deficits, then normalized
  group-load improvement with stable tie-breaking.
- Repair requires matching assigned/committed membership, a reachable leader,
  and a reachable quorum. Optional load rebalance requires every current voter
  to be reachable. No plan is created from cached topology.
- One control-plane mutation path and one active transition per resource prevent
  overlapping local plans. The reconciler waits for Catalog finalization before
  selecting the next shard move.
- The deterministic plan token binds resource identity, customer generation,
  tablet, tablet epoch, and target. Rust revalidates that fence and remains the
  sole authority for learner catch-up, joint consensus, removal, finalization,
  and durable reopen.
- Browser-safe status and the console now expose assigned, bootstrap, target,
  committed, and reachable voters plus requested/achieved zones and racks,
  exclusions, node topology, capacity, automatic-repair progress, and separate
  Go desired/observed versus Rust Catalog generation cursors. Policy-only
  updates retain the Catalog/tablet routing generation.
- The regional Compose model declares three distinct racks. The live Kubernetes
  campaign requests a voter evacuation through managed policy instead of
  directly calling the membership-plan endpoint.
- The compatible Dependabot console group updates
  `eslint-plugin-react-refresh` to 0.5.6 and `globals` to 17.12.0; locked
  formatting, lint, type, test, audit, and docs-only build gates remain green.

## Upgrade and configuration

No data, Catalog, Raft, EPRS, or native profile snapshot migration is required.
The protobuf and JSON contracts are additive. Existing placement records default
to one required rack, and a node without the new rack setting reports
`unassigned`. Existing Go status without `catalog_generation` safely adopts its
previously equal `observed_generation` during rolling upgrade.

Set a stable rack label on every regional node before requesting more than one
rack:

```shell
export EPOCH_REGIONAL_REGION=ap-south
export EPOCH_REGIONAL_ZONE=ap-south-1a
export EPOCH_REGIONAL_RACK=rack-a
export EPOCH_REGIONAL_NODE_CLASS=general-purpose
```

To evacuate a node, update the managed resource with that numeric node ID in
`spec.placement.excluded_node_ids` using the current expected generation. The
desired generation is committed first. A subsequent reconciliation pass plans
one repair, reports `pending`, and returns to `ready` after Rust finalizes the
target. Remove the exclusion only when the node is eligible to host data again.

Do not request `minimum_racks > 1` from the current Kubernetes operator topology
until node-label-derived rack attestation is implemented; its data nodes use
the safe `unassigned` default.

## Beta limitations

- Capacity is not transactionally reserved across several resources or Go
  control-plane owners. A newly committed learner may take one inventory cycle
  to affect another resource's placement decision.
- Load rebalance has deterministic monotonic scoring but no configurable
  hysteresis, drain budget, maintenance window, or fleet-wide evacuation
  progress object.
- Online partition split/merge, multi-voter plans, simultaneous-failure repair,
  and cross-resource placement transactions remain open.
- Kubernetes does not yet derive trusted region/zone/rack identity from node
  labels or a cloud provider. Its current node-name-as-zone behavior is an
  explicit development boundary.
- Protected exact-commit Kubernetes evidence, broader network/disk/partition
  chaos, load saturation, and published availability/recovery SLOs remain
  release-readiness gates.
